# 测试记录：2026-08-21 旧设备基准

## 测试目的

在新设备正式迁移前，用当前旧设备建立基准日志。

目标不是追求最终效果，而是确认：
- 日志是否能判断本地掉脸。
- 日志是否能判断 FPS/摄像头输入问题。
- 日志是否能区分本地处理问题和网络视频问题。

## 已确认事实

```text
摄像头实际输入：1280x720@10fps
处理输出帧尺寸：1280x720
OBS/DroidCam 配置：1280x720 / 30fps
```

这说明旧设备当前不是 1080p/30 输入，也不是 30fps 实时处理。

## 日志观察

稳定片段：

```text
process_fps 约 3.8-4.0
camera_fps 10.0
miss_rate 0%
bbox_jump 0-1
```

异常片段：

```text
miss_rate 可升到 60%-90%+
max_consecutive_missed 可到 20+ 帧
bbox_jump 偶发 2-3
```

## 初步判断

当前日志已经能支持判断大类问题：

1. 如果 `miss_rate` 高、`max_consecutive_missed` 高，是本地检测/掉脸风险。
2. 如果 `process_fps` 低但 `miss_rate` 不高，是性能/处理速度问题。
3. 如果本地日志稳定但 WhatsApp 远端糊，是网络/视频通话链路问题。
4. 如果 `bbox_jump` 多，是脸框跳动/贴合稳定性问题。

当前旧设备存在两个明确限制：

```text
摄像头实际只有 10fps
处理 FPS 多数时间低于 10fps
```

这会直接影响动态流畅度和远端观感。

## 仍然缺少的信息

需要动作标记，否则只能根据时间推测异常发生在哪个动作。

已新增可选脚本：

```text
6_MARK_TEST_EVENT.cmd
```

用途：

```text
测试时输入：开始静止 / 开始转头 / 快速转头 / WhatsApp变糊 / 结束
```

这些标记会写入 `live_health_YYYYMMDD.txt`，方便把异常指标和实际动作对应起来。

## 新设备复测要求

新设备必须按同一套动作复测：

1. 正脸静止 30 秒。
2. 正常说话 1 分钟。
3. 左右轻微转头。
4. 快速转头 2-3 次。
5. 低头/抬头。
6. WhatsApp 对方手机端观察。

新设备核心验收：

```text
camera_fps 是否达到 30
process_fps 是否接近 30 或至少稳定高于旧设备
miss_rate 是否明显降低
max_consecutive_missed 是否显著减少
bbox_jump 是否减少
WhatsApp 远端动态糊是否减少
```
