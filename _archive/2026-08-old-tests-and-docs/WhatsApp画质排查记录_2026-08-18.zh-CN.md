# WhatsApp 画质排查记录 2026-08-18

## 当前用户反馈

```text
WhatsApp 远端画质模糊。
换脸和不换脸都模糊。
DeepLiveCam / OBS Output 本地画面真实度不错。
流畅模式和质量模式在 WhatsApp 远端清晰度上差别不大。
```

## 当前正在运行的模式

最后一次日志显示：

```text
mode=low_latency
preset=low_latency
xseg=False
```

也就是当前测试的是流畅模式，不是质量模式。

## 当前 OBS / DroidCam 输出规格

OBS Profile：

```text
BaseCX=1280
BaseCY=720
OutputCX=1280
OutputCY=720
FPSCommon=30
DroidCamVirtualOutput AutoStart=true
```

OBS 场景：

```text
画布：1280x720
实际 DeepLiveCam 源画面区域：970x546
位置：X=155, Y=86
缩放：Lanczos
```

关键判断：

```text
虽然 DroidCam 给 WhatsApp 的画布是 1280x720，
但为了避免 WhatsApp 裁切，当前有效内容只有 970x546。
WhatsApp 再压缩后，远端会比本地 OBS 更糊。
```

所以当前不能简单说“720p 不够”或“1080p 一定更好”。真正问题是：

```text
1. OBS/DroidCam 输出给 WhatsApp 的画布是 720p。
2. 有效内容被安全边距缩小到 970x546。
3. WhatsApp 可能继续自适应压缩。
4. 对方手机端显示时还会再次缩放。
```

## 当前重点排查方向

### 方向 A：WhatsApp 直接真实摄像头是否也糊

目的：

```text
判断 WhatsApp 自身、网络、对方设备是否已经导致低画质。
```

测试：

```text
WhatsApp 摄像头选择 4k Camera。
不经过 OBS，不经过 DroidCam，不经过 DeepLiveCam。
对方手机观察清晰度。
```

结论：

```text
A 也糊：优先查 WhatsApp / 网络 / 对方设备 / 手机端视频通话效果。
A 清楚：继续查 OBS/DroidCam 链路。
```

### 方向 B：OBS + DroidCam 输出原始摄像头

目的：

```text
判断 OBS/DroidCam 虚拟摄像头链路是否导致画质下降。
```

测试：

```text
OBS 捕获真实摄像头 4k Camera。
OBS 输出 DroidCam Video。
WhatsApp 选择 DroidCam Video。
不经过 DeepLiveCam。
```

结论：

```text
B 糊：问题在 OBS/DroidCam/WhatsApp 虚拟摄像头链路。
B 清楚：问题回到 DeepLiveCam 输出或有效内容缩放。
```

### 方向 C：OBS + DroidCam 输出清晰测试画面

目的：

```text
判断 WhatsApp 是否把 DroidCam Video 当成低规格摄像头处理。
```

测试：

```text
OBS 输出清晰文字/线条/色块。
WhatsApp 选择 DroidCam Video。
对方手机观察文字边缘是否清晰。
```

结论：

```text
C 也糊：WhatsApp/DroidCam/网络是主要瓶颈。
C 清楚：换脸画面糊不是虚拟摄像头本身问题。
```

### 方向 D：最终 DeepLiveCam 链路

目的：

```text
验证最终使用效果。
```

测试：

```text
DeepLiveCam -> OBS -> DroidCam -> WhatsApp
分别测试质量模式和流畅模式。
```


## 2026-08-18 VPN/代理链路补充结论

用户反馈：
- Telegram 视频通话在相同 VPN 节点下与 WhatsApp 效果接近。
- 移动画面时传输明显变慢，画面卡糊，不只是静态清晰度问题。
- WhatsApp 的“减少通话流量”已关闭。
- 手机和手机、电脑和手机、高配置手机测试也会糊。

本机检查：
- Windows 系统代理开启：`127.0.0.1:8800`。
- Telegram 连接到本地代理端口，再由 QuickQ 服务转发。
- 旧日志中 `1.1.1.1` 延迟约 75ms；`8.8.8.8` 约 198ms 且有 timeout；`www.whatsapp.com` 多次 timeout。

判断：
- 当前最可疑区域已经不是 DeepLiveCam、OBS、DroidCam 或素材。
- 当前更像是实时音视频链路被 VPN/代理/节点/UDP 支持限制，导致 WhatsApp 和 Telegram 都降码率或走低质量中继。
- 如果代理只稳定处理 TCP，而音视频 UDP/TURN/STUN 走得不好，表现就是静态勉强能看，移动时糊、拖、卡。

下一步只测网络链路，不改换脸效果：
1. QuickQ 全局模式 vs 智能模式。
2. 不同节点，优先低延迟、支持 UDP、适合视频通话的节点。
3. 如 QuickQ 有 TUN/增强模式/UDP 转发/WebRTC 相关开关，逐项验证。
4. 同一场景下对比 Telegram 和 WhatsApp。
5. 记录远端观感：静止清晰度、快速移动拖影、延迟、是否掉帧。
