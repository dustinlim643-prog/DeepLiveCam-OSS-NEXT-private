# 稳定性与掉脸检测记录

## 当前原则

当前不做复杂兜底画面，不做自动冻结，不做自动切备用画面。

原因：
- 这些机制如果检测不准，会制造新的异常。
- 当前最重要的是先定义“什么叫掉脸”，并用日志验证误判率。
- 任何影响画面质量、换脸贴合、通话质量的动作，必须先单独说明并确认。

## 掉脸/异常的定义

当前先只记录，不自动处理。

优先关注这些信号：
- 连续检测不到目标脸。
- 检测到的人脸框突然大幅跳动。
- 人脸框面积突然大幅变化。
- 实时处理 FPS 明显低于目标帧率。
- 输入队列或输出队列持续堆积。

这些信号只说明“可能异常”，不能直接等于必须断通话。
未来如果要自动断通话，必须先证明这些指标稳定、误判低。

## 已新增日志

启动脚本默认加入：

```text
--live-health-log
```

日志文件：

```text
logs/live_health_YYYYMMDD.txt
```

每约 5 秒记录一次：

```text
process_fps
camera_fps
frames
detected
missed
miss_rate
max_consecutive_missed
bbox_jump
avg_bbox_area
queue_in
queue_out
```

隐私边界：
- 不保存画面。
- 不保存人脸图片。
- 不截图。
- 不记录源图路径之外的面部数据。
- 只记录数字状态。

## 未来可选优化

暂不执行，只记录：

1. 掉脸检测阈值校准。
2. 异常时提示而不是自动处理。
3. 异常次数统计报表。
4. 严重异常时手动一键停止通话链路。
5. 在确认误判率足够低后，再考虑自动断开通话。

## 当前结论

现在不应把重点放在花哨保护机制上。
正确顺序是：

1. 先收集稳定性日志。
2. 根据日志判断掉脸是否真实发生。
3. 区分本地换脸掉脸、FPS 过低、网络视频卡顿。
4. 再决定是否需要自动动作。
