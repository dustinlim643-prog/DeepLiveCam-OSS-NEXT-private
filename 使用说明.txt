DeepLiveCam OSS_READY 最终使用说明

项目目标：
实时单图换脸，输出到 OBS，再通过 DroidCam Video 给 WhatsApp Desktop 使用。

当前正式链路：
DeepLiveCam OBS Output 窗口
-> OBS 捕获该窗口
-> DroidCam Virtual Output
-> Windows 设备 DroidCam Video
-> WhatsApp Desktop 选择 DroidCam Video

根目录日常只用四个入口：

1. 启动
1_START_LOW_LATENCY.cmd

2. 停止
2_STOP.cmd

3. 查看最近健康日志
3_SHOW_RECENT_HEALTH.cmd

4. 生成一次完整稳定性诊断快照
4_CAPTURE_STABILITY_SNAPSHOT.cmd

5. 诊断 WhatsApp 视频链路
5_DIAGNOSE_WHATSAPP_VIDEO.cmd

不要再使用 OBS Virtual Camera 作为 WhatsApp 摄像头。
WhatsApp 里选择 DroidCam Video。

启动步骤：

1. 双击 1_START_LOW_LATENCY.cmd。
2. 等 DeepLiveCam 界面、OBS、OBS Output 窗口出现。
3. DeepLiveCam 里确认源脸图片和摄像头。
4. 点击 Live / 直播。
5. OBS 预览里应能看到 OBS Output 窗口画面。
6. WhatsApp 设置 -> 视频和语音 -> 摄像头选择 DroidCam Video。
7. 发起视频通话，通话中的摄像头菜单也选择 DroidCam Video。

当前推荐配置：

摄像头输入：1280x720 / 30fps，MJPG
OBS 画布：1280x720 / 30fps
WhatsApp 摄像头：DroidCam Video
主换脸模型：HyperSwap 256
Face Enhancer：None
XSeg：低延迟模式默认关闭
GPEN512：默认关闭

为什么关闭 GPEN512：

GPEN512 是后处理增强，不是主换脸模型。
它会明显增加延迟和掉帧。
当前测试显示关闭后处理 FPS 从约 7fps 提升到约 18-26fps。
如果后续要增强清晰度，先试 GPEN-256，不直接回到 GPEN-512。

没有画面的排查顺序：

1. Windows 设备里是否有 DroidCam Video：
   Get-PnpDevice | Where-Object FriendlyName -match 'Droid|OBS|Camera' | Format-Table Status,Class,FriendlyName -AutoSize

2. OBS 是否加载 DroidCam 插件：
   OBS 日志里应出现 droidcam-virtual-output.dll 和 AutoStart Trigger。

3. OBS 预览是否有 DeepLiveCam 画面：
   如果 OBS 里黑屏，问题在 OBS 窗口捕获。

4. WhatsApp 是否选择 DroidCam Video：
   如果选了 DroidCam Video 但没画面，问题通常在 OBS 没有把画面输出给 DroidCam。

5. 如果刚安装 DroidCam 驱动或插件，重启电脑后再测。

新设备 WhatsApp 选择 DroidCam Video 但没有换脸画面：

先运行：
5_DIAGNOSE_WHATSAPP_VIDEO.cmd

重点看：

1. OBS profile 是否是 DeepLiveCam。
2. DroidCam AutoStart 是否是 true。
3. OBS scene 是否捕获 OBS Output:HighGUI class:python.exe。
4. OBS 日志是否有 droidcam-virtual-output.dll loaded。
5. OBS 日志是否有 webcam video active 1280x720 30fps。

如果 WhatsApp 画面显示 Start DroidCam 或黑屏，但 OBS 预览有换脸画面，问题通常在：

1. OBS 没有真正启动 DroidCam Virtual Output。
2. OBS 使用了错误 profile。
3. WhatsApp 读到了 DroidCam 的旧占位流。
4. 启动顺序不对。

正确顺序：

1. 先运行 2_STOP.cmd。
2. 再运行 1_START_LOW_LATENCY.cmd。
3. 等 OBS Output 窗口出现并有画面。
4. 等 OBS 预览有画面。
5. 再打开 WhatsApp，选择 DroidCam Video。

当前已知问题：

1. 脸部最外轮廓还不够紧致贴合。
2. 动作过大、侧脸、低头时可能出现边缘穿模。
3. WhatsApp 最终画质受网络、压缩、DroidCam 输出和 OBS 输入共同影响。
4. 说话时嘴唇可能偏死板，属于单图实时换脸常见问题。
5. 边缘问题和嘴唇问题暂时不混调，先保证 WhatsApp 链路稳定。

后续边缘优化顺序：

1. 固定同一张源图、同一光线、同一摄像头位置。
2. 先微调 face_fit_scale。
3. 再调 mask scale / blur。
4. 再测试 XSeg。
5. 最后才加 OBS 轻微锐化/柔化。

嘴唇死板优化顺序：

该问题排在脸部边缘优化之后。
优先方向不是盲目增强画质，而是保护目标嘴部动态：

1. 先测试 mouth mask / mouth region protection。
2. 再测试减少嘴唇区域换脸强度，让真实嘴形和牙齿保留更多。
3. 再筛选嘴唇颜色更自然、闭嘴或轻微微笑的源图。
4. 最后才考虑外部 lip-sync / expression-restorer 类方案。

取舍：

保护目标嘴部会让说话更自然，但身份相似度可能略降。
完整 lip-sync 效果更强，但实时视频通话链路复杂度和延迟会明显增加。

日志位置：

项目内日志：
logs

完整诊断快照：
logs\stability_snapshot_YYYYMMDD_HHMMSS.txt

帧率稳定性排查：

1. 启动 1_START_LOW_LATENCY.cmd。
2. WhatsApp 接通后保持 2-3 分钟。
3. 不同时改源图、XSeg、GPEN、OBS 滤镜。
4. 测试结束后先运行 4_CAPTURE_STABILITY_SNAPSHOT.cmd。
5. 如果只想快速看最近几行，再运行 3_SHOW_RECENT_HEALTH.cmd。
6. 重点看 live_health 里的：
   process_fps
   camera_fps
   miss_rate
   queue_in / queue_out
   avg_ms_total
   avg_ms_detect
   avg_ms_swap
   avg_ms_enhance
   avg_ms_other

判断方式：

avg_ms_detect 高：瓶颈在人脸检测/追踪。
avg_ms_swap 高：瓶颈在 HyperSwap 主换脸。
avg_ms_enhance 高：说明开了 GPEN/GFPGAN 或增强器负担过重。
queue_in 长期满：处理跟不上摄像头输入。
miss_rate 高：掉脸/侧脸/遮挡/距离问题，先不等同于网络问题。

断线/掉帧保护阶段：

现在只做日志和判断，不自动挂断 WhatsApp。
自动断线必须等多轮日志证明误判率低之后再考虑。

4_CAPTURE_STABILITY_SNAPSHOT.cmd 会记录：

1. DeepLiveCam 处理 FPS、摄像头 FPS、掉脸率、队列、分段耗时。
2. OBS 是否捕获 OBS Output，DroidCam 输出是否 active/inactive。
3. Windows 是否识别 DroidCam Video、OBS、4k Camera。
4. WhatsApp 进程和连接状态。
5. 网络延迟和丢包快速样本。

问题归因顺序：

1. process_fps 低或 queue 高：本地处理跟不上。
2. camera_fps 低：摄像头输入规格或驱动问题。
3. miss_rate 高：本地掉脸、遮挡、侧脸或脸部距离问题。
4. OBS 里 DroidCam inactive/stopping：OBS 到 DroidCam 输出链路问题。
5. 本地输出清楚但远端糊，且网络延迟/丢包异常：优先看 VPN/网络。
6. 本地输出清楚、网络正常但远端糊：优先看 WhatsApp 压缩或虚拟摄像头接收规格。
